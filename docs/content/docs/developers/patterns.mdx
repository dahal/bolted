Four patterns recur across nearly every package. Once you see them, the codebase reads predictably.

## 1. Indirection vars for external calls

Anywhere production code calls out to the OS — `os.Open`, `exec.Command`, `runtime.GOOS`, `debug.ReadBuildInfo`, even pure stdlib helpers like `json.MarshalIndent` whose error branch is unreachable in practice — we wrap it in a package-level `var` so tests can swap the implementation.

The pattern, taken from `internal/buildinfo/buildinfo.go`:

```go
// readBuildInfo is the indirection point that lets tests substitute
// a fake implementation, exercising fromDebug's branches that
// wouldn't otherwise fire from inside `go test`.
var readBuildInfo = debug.ReadBuildInfo

func fromDebug() (version, commit string) {
    info, ok := readBuildInfo()  // not the direct stdlib call
    if !ok {
        return "", ""
    }
    // …
}
```

The test:

```go
func TestFromDebug_NoBuildInfo(t *testing.T) {
    orig := readBuildInfo
    t.Cleanup(func() { readBuildInfo = orig })
    readBuildInfo = func() (*debug.BuildInfo, bool) { return nil, false }

    v, c := fromDebug()
    if v != "" || c != "" { … }
}
```

Why we don't use dependency injection through function arguments: it pollutes the surface area for the 99% of callers who just want the default. Package vars cost one line of wiring; everyone uses the production impl unless a test deliberately swaps it.

Examples across the codebase:
- `internal/buildinfo/buildinfo.go` — `readBuildInfo`
- `internal/backend/factory/factory.go` — `runtimeGOOS`
- `internal/cli/password.go` — `isTerminalFn`, `readPasswordFn`
- `internal/cli/lifecycle.go` — `newBackendFn`, `loadConfigFn`, `saveConfigFn`, `newPrompterFn`, `newVolumeFn`, `detectDefaultsFn`, `boltedDirFn`
- `internal/cli/dev_cmd.go` — `newRunnerFn`, `stateDirFn`, `trustGateFn`, `confirmTrustFn`
- `internal/volume/volume.go` and `internal/backend/lima/lima.go` — `yamlMarshal`, `jsonMarshalIndent` (the latter literally cannot fail for `map[string]int`; we wrap it anyway so coverage can hit the error branch)
- `internal/cli/status_cmd.go` — `statFn`
- `internal/cli/shell_cmd.go` — `stdinFn`

### When to add one

If your code calls a stdlib function whose **error branch can't fire in the test environment** (e.g. you'd need a read-only filesystem, a missing build, an actual TTY), add an indirection var. If you don't, that branch stays uncovered forever.

### When *not* to

Pure functions don't need indirection — their inputs are already controllable. `parseSize("8GB")` doesn't need a `parseSizeFn` var; tests just call it with different strings.

## 2. Accept interfaces, return concrete

Go's standard advice, taken seriously here. Functions accept the smallest interface they need; constructors return the concrete type so callers don't lose access to type-specific behaviour.

Where this shows up: the orchestration packages each *return* a concrete `*Volume`, `*Manager`, `*Backend`, `*Store`. Consumers that need to mock them define a local interface listing only the methods they call. From `internal/cli/lifecycle.go`:

```go
// volumeOps is the slice of *volume.Volume the lifecycle commands
// actually use. Defining it here (and not in package volume) keeps
// the accept-interfaces / return-concrete pattern intact and lets
// tests inject a stub without exporting more from internal/volume.
type volumeOps interface {
    Create(ctx context.Context, imagePath string, sizeBytes int64, password []byte) error
    Open(ctx context.Context, imagePath string, password []byte) (volume.Device, error)
    Mount(ctx context.Context, dev volume.Device, mountpoint string) error
    Unmount(ctx context.Context, mountpoint string) error
    Close(ctx context.Context, dev volume.Device) error
}
```

`volume.New` still returns `*volume.Volume`. The `lifecycle` package defines its narrow `volumeOps` view locally because that's what `runUnlock` and `runLock` actually need. `passwd_cmd.go` defines a separate `passwdVolume` interface that includes `AddKeyslot`/`RemoveKeyslot` because that's what *it* needs.

The benefit: the `volume` package's exported surface stays minimal, and the lifecycle package's tests can satisfy `volumeOps` with a fake without re-implementing `*volume.Volume`.

## 3. Sentinel errors + `errors.Is`

Whenever the caller might want to recognise a specific failure category, we expose a sentinel error and wrap concrete failures with `fmt.Errorf("…: %w", sentinel)`:

- `volume.ErrBadPassword` — wrong LUKS passphrase
- `devcontainer.ErrContainerExists` — `Up` called twice on the same repo
- `devcontainer.ErrDevcontainerMissing` — devcontainer CLI not installed
- `devcontainertrust.ErrNoConfig` — repo has no `.devcontainer/devcontainer.json` (gate becomes a no-op)
- `devcontainertrust.ErrNoTTY` — interactive trust prompt with non-TTY stdin
- `keychain.ErrNotFound` — keychain entry missing
- `provision.ErrXxx` (per the package's needs)

Callers use `errors.Is(err, volume.ErrBadPassword)` to branch — never string-matching, never type assertion against `*xxxError`. The wrap layer carries context (`fmt.Errorf("cryptsetup open %s: %w", path, volume.ErrBadPassword)`) so the rendered message is useful, but the programmatic check stays clean.

The exit-code machinery (`internal/cli/lifecycle.go::exitError`) follows the same shape: the type is unexported, recognised via `errors.As`, and lets typed errors flow through Cobra's `RunE` return path.

## 4. Build-only-on-target with runtime fallback for testing

Per-OS code (Lima only matters on Mac, WSL2 only on Windows) is split two ways depending on whether we need the package to *compile* everywhere:

**Build tag, compile only on target.** Used for code that genuinely can't compile elsewhere — e.g. `internal/hostinfo/hostinfo_windows.go` uses `golang.org/x/sys/windows.MemoryStatusEx` which has no darwin equivalent:

```go
//go:build windows

package hostinfo

import "golang.org/x/sys/windows"
// …
```

`internal/keychain/keychain_darwin.go`, `keychain_windows.go`, `keychain_other.go` follow the same pattern.

**Runtime guard, compile everywhere.** Used when the package needs to be unit-testable on the dev host but actually run only on the target OS. `internal/backend/wsl2/wsl2.go` does this with `currentGOOS` + `requireWindowsFn`:

```go
var currentGOOS = runtime.GOOS

var requireWindowsFn = defaultRequireWindows

func defaultRequireWindows() error {
    if currentGOOS == "windows" { return nil }
    return fmt.Errorf("wsl2 backend: cannot run on %s; …", currentGOOS)
}
```

Production: refuses to start on macOS. Tests: swap `requireWindowsFn` to a no-op so the wsl2 unit tests can exercise the full code path on the dev host.

When to use which:
- **Build tag** if the implementation calls APIs that don't exist on other OSes.
- **Runtime guard** if the implementation is pure logic that *would* work but you want to refuse to start production accidentally on the wrong OS.

## 5. End-to-end gating with `BOLTED_E2E=1`

Anything that touches a real backend (Lima, WSL2, cryptsetup, podman) is split into two test files per package:

- `xxx_test.go` — unit tests with mocked backends. Run on every `go test ./...`. Target 100% coverage.
- `xxx_e2e_test.go` — integration tests against real hardware. **Skipped unless `os.Getenv("BOLTED_E2E") == "1"`** (and on some packages, gated by `runtime.GOOS` as well).

The pattern, from `internal/volume/volume_e2e_test.go`:

```go
func TestVolumeLifecycleE2E(t *testing.T) {
    if os.Getenv("BOLTED_E2E") != "1" {
        t.Skip("e2e tests gated by BOLTED_E2E=1")
    }
    if runtime.GOOS != "linux" {
        t.Skip("requires dm-crypt; run on a real Linux host")
    }
    // … real create / open / mount / unmount / close cycle
}
```

Why an env var instead of a build tag: e2e tests live alongside the unit tests in the same package, share helpers, and only differ in whether they spawn real processes. A build tag would force two packages or noisy `//go:build` annotations on every file. Env-var skip is one line per test and CI explicitly opts in.

See [Testing strategy](/docs/developers/testing) for the broader story.

## Pulling it together

A new package implementing some "talks to the VM" feature typically looks like:

```go
package thing

import (
    "context"
    // …
    "github.com/dahal/bolted/internal/backend"
)

// ErrXyz is the typed failure for the most common error users
// might want to recognise.
var ErrXyz = errors.New("thing: xyz")

// thingDoSomething shells out via Backend.Exec. The thingFn
// indirection lets tests swap a recorded implementation.
var thingFn = realDo

func realDo(ctx context.Context, b backend.Backend, …) error {
    // …
}

func Do(ctx context.Context, b backend.Backend, …) error {
    return thingFn(ctx, b, …)
}
```

…with `internal/thing/thing_test.go` exercising every branch via the mock backend, and `internal/thing/thing_e2e_test.go` (if applicable) gated behind `BOLTED_E2E=1`.

<Callout>
If you find yourself writing a test that depends on the *real* OS behaviour (a real TTY, a real file with a real mode, the real `runtime.GOOS`), reach for an indirection var instead. Coverage gaps that look like "this branch can't be tested" almost always mean a missing seam, not a real limitation.
</Callout>
